# Movix Vodix —27 November2026

Vodix is a distinct public Movix integration, not another Vidara alias. Current
Sources FR/native/+ discovery queries Custom, Omega and SwiftFlow, but does not
query Vodix. This investigation makes no production resolver or version changes.

## Discovery and availability

Movix's first-party application discovers `https://api.movix.tokyo`. Its registry
loads `vodixService-CmKKuv8Y.js`; movie/TV watch pages call that service separately
from their existing source lists. The service provides:

- `/api/vodix/movie/{tmdbId}`;
- `/api/vodix/tv/{tmdbId}/{season}/{episode}`;
- `/api/vodix/4k` for available/upcoming titles.

The captured4K catalogue contained84 available titles. See the
[sanitized snapshot](../../tests/evidence/vodix-2026-11-27.json) for its update
time, movie/TV breakdown and fingerprints. Dune: Part Two693134, Harry Potter and
the Deathly Hallows Part112444, and Game of Thrones1399 S1E1 returned a2160p MULTI
source. Avengers: Age of Ultron99861, Interstellar157336 and The Matrix603 returned
empty source lists. This is a limited catalogue, not universal4K coverage.

No user account or VIP token was supplied. The website marks these discovered
entries non-VIP; public discovery and two playback exchanges succeeded. This is
not a claim that every source is anonymously playable or available permanently.

## Playback protocol

The API returns a base origin, file code, quality/language and optional label.
The first-party service requests `/e/{code}/challenge`, computes a bounded SHA256
nonce for the issued challenge, POSTs it to the supplied same-origin endpoint and
uses the returned same-origin HLS URL. Captured challenge difficulty was16bits;
Python hash-loop wall time was31–206ms on the cloud machine. Successful exchange
through master retrieval took approximately0.7–0.8s, excluding initial discovery,
metadata translation, subtitles and media startup. These are not TV speed claims.

Use fresh capabilities and the normal site request headers. Requests without the
normal Origin/Referer initially returned403; subsequent normal-flow exchanges
worked, but further challenge/playlist/media requests also intermittently returned
403. The exact cause (expiry, request binding, server policy or cloud networking)
was not established. Do not remove signed arguments or cache grants to hide this.

Caption discovery uses `subtitles.json` and `external-subtitles` relative to the
playback URL. The first-party service distinguishes text from bitmap/PGS tracks,
normalizes languages and retains forced/full labels. Native integration must not
return PGS as if it were a downloadable VTT/SRT text caption.

## Quality and languages

Two retrieved HLS masters advertised:

| Case | Dimensions | Video/HDR declaration | Audio groups | Caption inventory |
| --- | --- | --- | --- | --- |
| Game of Thrones S1E1 |3840×2160 |HEVC Main10 declaration, PQ |French / English |French forced/full and English full text; French PGS also listed |
| Harry Potter7 Part1 |3840×1600 |HEVC Main10 declaration, PQ |French VFQ, French VFF, English |French forced/full, English full text and separate PGS tracks |

3840×1600 is a cropped widescreen4K raster. Do not confuse it with a1080p source
or claim an unobserved2160-line image. Audio display names mention DTS, TrueHD or
DDP, while the master CODECS field advertises AAC. Those labels do not prove the
actual delivered audio codec/channel count; proper initialization/media probing
is still required.

Media samples returned `image/jpeg` with a JPEG prefix followed by MP4 fragment
boxes. Initial generic range/prefix sampling did not yield a valid movie codec
inventory. Whether exact HLS byte ranges or additional browser handling are needed
was not established: fresh detailed probes hit403. This does **not** prove the
stream is broken, nor that it requires a proxy. Full ExoPlayer/libmpv and physical
TV playback remain unverified. A readable master alone is not a playback pass.

## Integration recommendation

Worth adding as its own bounded Movix discovery worker inside the existing
Sources FR/native/+ product, preserving one grouped banner. This keeps the4K path
from being skipped because unrelated Custom sources already filled their target.
Use exact advertised identities, fresh exchanges, original masters, all audio
tracks, clear quality/HDR labels and separately classified text captions. Preserve
current720p minimum, unknown-resolution policy, stable ordering and mapping guards.

Movies can be investigated independently of episode-order translation. Series
must establish the backend's actual episode layout before enabling translation
from a TVDB-ordered profile; a TMDB ID alone does not prove matching seasons.

The Android host also needs a transport prerequisite: current `HttpBridge`
accepts GET/HEAD only and `Engine.BOOTSTRAP` drops fetch request bodies. Vodix's
exchange requires POST JSON. This also limits existing POST-based FR resolvers,
including Vidara, in the hosted app. Native phone plugin transport supports that
request form. An Android runtime/bridge update is required; an engine-only package
cannot repair a missing native HTTP contract. Keep compatibility requirements
explicit rather than advertising unsupported host playback.

Before release: verify fresh renewal, anonymous access, failed challenges,
request/header isolation, both literal plugin wrappers, selected episode identity,
actual video and preferred audio initialization/segments, captions, HTTP range
behaviour, and real ExoPlayer/libmpv startup. Then publish native/+ artifacts and a
compatible authenticated host engine. No code change is justified by an unverified
4K badge or cloud403 alone.
